> **CP هنا = العلاقة (Couple Pairing):** اتنين مرتبطين بهدية CP اتقبلت. مالهاش علاقة بإعداد «قوة الحساب» القديم `cp_per_coin` / `cpPoints` اللي في صفحة الإعدادات.

## 1. الملخص

- **فتح CP بقى له سياسة:** مجاني أو برسوم، للكل أو لمستخدم معيّن. السيرفر هو اللي بيقرر وهو اللي بيخصم.
- **التطبيق بيعرض الرسوم قبل التأكيد:** مفيش خصم غير بعد «موافق»، والخصم ذري. لو الرصيد مش كافي بتظهر رسالة بالناقص ومفيش أي خصم.
- **مستوى الـ CP وقيمته من السيرفر.** «المستخدم الظاهر» كمان بقى متخزّن على السيرفر بدل الجهاز.
- **لوحة التحكم فيها تبويبين جداد:** «CP — العلاقة» و«الخلفيات».
- **كل عملية أدمن بتتسجّل** في `admin_audit_logs`: مين عمل إيه، لمين، القيمة قبل وبعد، الوقت، والـ IP.
- **الافتراضيات مش بتغيّر حاجة لأي مستخدم حالي** لحد ما المسؤول يقرر بنفسه.

### 2.2 لوحة التحكم (`backend/public/admin-dashboard.html` + `app.js`)

vanilla JS بنفس أسلوب الصفحة، ومن غير أي framework جديد. كل النداءات بتروح على المسارات اللي في `adminCp.routes.ts` بس.

**تبويب «CP — العلاقة»:**
1. **سياسة الفتح:** مجاني أو برسوم وعدد الكوينز، وقيمة رفع المستوى، وأقصى مستوى، وأسماء المستويات. الحفظ بيطلب تأكيد.
2. **صلاحية مستخدم معيّن:** «فتح CP مجانًا» أو «فتح CP برسوم» بالـ Display ID مع ملاحظة، وجدول بالصلاحيات الحالية فيه عرض وسحب.
3. **بيانات CP لمستخدم:**
   - الرصيد، وحالة الفتح ومصدره، والسياسة اللي عليه، والمستخدم الظاهر، والدعوات المعلّقة.
   - أزرار فتح وقفل CP له.
   - جدول الأزواج: تعديل قيمة CP، وتثبيت المستوى (فاضي = تلقائي)، واختيار المستخدم الظاهر، وفك الارتباط.
4. **هدايا CP:** السعر والاسم بالعربي والترتيب والتفعيل.
5. **سجل العمليات:** فلتر بالمستخدم وبنوع العملية (CP / خلفيات / الكل)، و«تحميل المزيد».

**تبويب «الخلفيات»:**
1. **إضافة:** رفع صورة أو فيديو mp4/webm، مع الاسم، ومجانية أو السعر، والمدة (فاضي = أبدي)، و«خاصة (خارج المتجر)».
2. **كل الخلفيات:** معاينة، وتعديل مباشر في الجدول، وعدد الملّاك، وحذف بتأكيد بيوضّح كام مستخدم هيفقدها.
3. **منح / سحب لمستخدم:** مع سبب السحب.
4. **خلفيات مستخدم:** اللي بيملكه، وتاريخ الانتهاء، والمركّبة حاليًا، وسحب.
5. **زرار «سجل العمليات»:** بيفتح سجل تبويب CP متفلتر على عمليات الخلفيات.

## 3. الـ Migration وحفظ البيانات الحالية

`20260922000000_cp_permissions_admin` **إضافي بالكامل (additive)**. كل الأوامر فيه `IF NOT EXISTS` أو `ON CONFLICT DO NOTHING`، وممكن يتشغّل أكتر من مرة من غير مشاكل.

**اللي بيتضاف:**
- `users.cpFeaturedPartnerId`
- `cp_pairs.cpValue` (افتراضي 0) و`cp_pairs.levelOverride` و`cp_pairs.updatedAt`
- جداول: `cp_unlock_grants` (منحة واحدة لكل مستخدم)، `cp_unlock_grant_history` (ما بيتمسحش أبدًا)، `cp_unlocks` (واحد لكل مستخدم)، `admin_audit_logs`

**الـ backfill (حفظ اللي موجود):**
1. **`cpValue`:** كل زوج بياخد قيمة الهدية اللي عملت الارتباط، من آخر طلب CP مقبول بين الاتنين. الزوج اللي مالوش طلب مطابق بيفضل 0، ومع الإعدادات الافتراضية ده ما بيغيّرش حاجة في العرض.
2. **`cp_unlocks`:** أي حد عنده زوج CP، أو بعت طلب CP واتقبل قبل كده، بيتسجّل إنه **فاتح CP مجانًا** (`source = 'legacy'`). لو المسؤول حوّل السياسة لـ«برسوم» بعدين، المستخدمين دول مش هيتقفل عليهم.
3. **الإعدادات:** `cp_unlock_mode = free`، و`cp_unlock_fee_coins = 0`، و`cp_level_step_coins = 0`، و`cp_level_max = 5`. بتتضاف **بس لو مش موجودة**.

**اللي ما بيتلمسش:** مفيش أي صف في `users` أو `user_items` (ملكية الخلفيات) أو `cp_pairs` بيتمسح، ومفيش عمود موجود بيتكتب عليه. **مستوى كل زوج حالي فاضل زي ما هو بالظبط**، لأن `cp_level_step_coins = 0` معناها استخدام سلّم الأيام القديم (0/7/30/90/365 يوم).

**الرجوع (rollback):** يكفي ترجّع الكود القديم. الجداول والأعمدة الجديدة مش بتأثر على الكود القديم، ومفيش داعي تمسحها.

## 4. الافتراضات والقرارات

1. **«فتح CP»** معناه صلاحية إرسال دعوة CP (وبالتالي عمل ارتباط)، والرسوم بتتدفع **مرة واحدة** لكل حساب.
2. **الـ spec الأصلي كان مقطوع عند «بعد موافقة…».** التفسير المتفق عليه: بعد التأكيد تتخصم الكوينز ذريًا، ويتفتح CP، وتتسجّل العملية. ولو الرصيد مش كافي تظهر رسالة بالناقص ومفيش خصم.
3. **التطبيقات القديمة شغّالة زي ما هي:** طول ما السياسة «مجاني»، السيرفر بيسجّل الفتح تلقائيًا ساعة الدعوة.
4. **المنح من اللوحة ما بيخصمش كوينز.** «فتح CP برسوم» معناه إن المستخدم نفسه هو اللي بيدفع السعر ده لما يأكد من التطبيق. أما «فتح CP له مجانًا الآن» فبيفتحه فورًا.
5. **قفل CP لمستخدم** بيمنع الدعوات الجديدة بس. الارتباطات الحالية بتفضل، ومفيش استرجاع لأي رسوم.
6. **قيمة CP** = مجموع الكوينز المتبادلة بين الشريكين كهدايا، بداية من هدية القبول. **المستوى** = `1 + floor(القيمة / قيمة رفع المستوى)` بحد أقصى `cp_level_max`، ولو قيمة الرفع 0 بيتحسب بالأيام. تثبيت المستوى من الأدمن بيغلب الاتنين.
7. **المستخدم الظاهر** اختيار **صاحب الصفحة**، فالزائر بيشوف نفس اختياره. لو مفيش اختيار بيظهر أحدث زوج.
8. **سحب الخلفية** بيمسح صف (المستخدم، الخلفية) للمستخدم ده بس، ولو كانت مركّبة على صفحته بتتشال. **حذف الخلفية** بيشيلها من كل اللي بيملكوها (نفس سلوك حذف منتج من المتجر)، وعدد الملّاك بيتسجّل في الـ audit.
9. **قيمة CP مش ظاهرة في التطبيق.** التطبيق بيقراها بس ما بيعرضهاش، عشان ما نغيّرش تصميم الكارت من غير موافقة العميل.

### على بيئة الاختبار (staging) الأول

1. **الكود:** `git fetch && git checkout feat/cp-permissions-admin`
2. **الـ backend:** السكربت `backend/deploy.sh` بيعمل الخطوات دي بالترتيب:
   ```bash
   cd backend
   npm install
   npx prisma generate
   npm run build
   npx prisma migrate deploy      # مش db push
   pm2 restart samafox-api
   ```
3. **اتأكد إن الـ migration اتطبّق:**
   ```sql
   SELECT COUNT(*) FROM cp_unlocks WHERE source = 'legacy';   -- ≥ عدد اللي عندهم زوج CP (وبيشمل اللي بعتوا طلب اتقبل)
   SELECT key, value FROM app_settings WHERE key LIKE 'cp_%';
   ```
4. **التطبيق** (على جهاز فيه Flutter SDK):
   ```bash
   cd app
   flutter pub get
   flutter analyze
   flutter test
   flutter build apk --release
   ```
   ونزّل الـ APK على أجهزة التجربة. اتأكد إن النسخة دي متوجّهة لسيرفر الـ staging مش الإنتاج.

- [ ] سحبها من مستخدم واحد: تتشال من صفحته بس، ومستخدم تاني بيملكها ما يتأثرش.
- [ ] محاولة وضع خلفية مدفوعة مش مملوكة من التطبيق بتترفض بـ `BACKGROUND_NOT_OWNED`.

**سجل العمليات:**
- [ ] كل خطوة فوق ليها صف فيه المسؤول والعملية والمستخدم وقبل/بعد والـ IP.

### للإنتاج (production)
بعد ما كل اللي فوق يعدّي على الـ staging: نفس الخطوات، والإعدادات تفضل «مجاني» لحد ما العميل يقرر. **ارفع نسخة التطبيق الجديدة على المتجر قبل ما تحوّل السياسة لـ«برسوم»**، عشان النسخ القديمة بتعرض رسالة خطأ بدل dialog الدفع.

## 7. متابعات معروفة

- تشغيل `flutter analyze` / `flutter test` وتجربة التطبيق فعليًا. **دي أهم خطوة قبل النشر.**
- تشغيل الـ migration على نسخة من داتابيز الإنتاج على الـ staging.
- اختبار مباشر لـ `setFeaturedPartner` ومسارات `/cp` بعد بناء `bcrypt` (`npm rebuild bcrypt`).
- عرض «قيمة CP» في كارت العلاقة لو العميل عايز.
- جدول الخلفيات في اللوحة بيتسكرول بالعرض على الشاشات الضيقة، زي باقي جداول اللوحة.
