## How admin authority currently works

- Dashboard login is implemented in `backend/src/routes/admin-dashboard-auth.routes.ts::POST /login`; it can reuse public login and otherwise checks credentials directly. It sets an HttpOnly `access_token` cookie. Protected API access still goes through authentication and a database-backed admin check; possessing the static HTML is not authority.
- `requireAdminDashboard` checks **only `User.isAdmin`**. `requireSuperAdmin` additionally checks `User.isSuperAdmin`. By contrast, `adminMiddleware` accepts either flag. This inconsistent treatment matters for a super-admin account without `isAdmin`.
- `backend/src/routes/adminDashboard.routes.ts` applies `authenticate` and `requireAdminDashboard` to the router. Only selected mutations, such as admin-roster changes and some economy controls, add `requireSuperAdmin`. Product CRUD under `/api/v1/admin-products` and gift CRUD under `/api/v1/admin/gifts` use the broad `adminMiddleware`; general dashboard gift prices, VIP/level configuration and agency controls do not consistently require a separate financial permission.
- Delegated staff authority is a different system. `staffRules.ts` defines `MANAGER > SUPER_ADMIN > ADMIN`, appointment hierarchy, grant caps, and permission keys including `grant_vip`, `grant_level`, `grant_frame`, `grant_entry`, `grant_bubble`, `manage_host_agency`, `follow_agencies`, and `ban_users`. `staff.service.ts::resolveAccess` filters active/unexpired roles and permissions and derives descendant/agency scope. A `MANAGER` receives all current catalog keys automatically. Staff role assignment is not assignment of `User.isAdmin` / `isSuperAdmin`.
- `backend/src/staff/__tests__/moneySeparation.test.ts` explicitly checks that delegated staff services do not write coins, product definitions, platform flags, or charging agencies. That separation is useful but does not protect legacy platform-admin endpoints.
- There is no explicit `OWNER` role or owner-issued financial permission catalog matching item 42. Super-admin gates are not equivalent to owner authorization. Extend this system deliberately; do not make newly added financial permissions automatically available through the manager's “all permissions” rule.
- `backend/public/app.js`, `staff-admin.js`, and `economy-admin.js` are presentation layers, not enforcement. The separate `backend/public/gifts-admin/app.js:27–46` calls `/api/v2/admin/gifts`, whereas `backend/src/index.ts:229–230` mounts `/api/v1/gifts` and `/api/v1/admin/gifts`. No matching v2 Express mount was found. A deployment proxy rewrite could affect this, but was not verified. There is also a v1 routing collision: `index.ts:155` mounts `backend/src/routes/admin.routes.ts` first; its legacy `GET/POST /gifts` and `PATCH/DELETE /gifts/:id` intercept overlapping gift CRUD requests before the canonical gift router. Category mutations have the longer `/gifts/categories/:id` path and do not match that legacy single-parameter route. Correct both prefix and overlapping gift CRUD contracts during gift-admin work; changing the frontend prefix alone is insufficient.

## Prisma migration conventions

- `backend/prisma/migrations/migration_lock.toml` declares `provider = "postgresql"`. The baseline is `0_init/migration.sql`; subsequent directories generally use a 14-digit timestamp and snake-case description, e.g. `20261004120000_staff_roles/migration.sql`. Two directories have the `20260903000000` prefix, so the current tree does not guarantee unique timestamp prefixes.
- Each migration contains plain PostgreSQL SQL, not a TypeScript runner or paired up/down files. The baseline uses Prisma-style `-- CreateEnum`, `-- CreateTable`, constraints and indexes. Later migrations are often hand-written, commented, and rerun-tolerant: quoted mapped table names, `CREATE TABLE/INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `SERIAL`, `TIMESTAMP(3)`, `JSONB`, arrays, and explicit defaults.
- `20260926000000_economy_cp_rooms_features/migration.sql` demonstrates additive columns/tables and a backup note. `20260922000000_cp_permissions_admin/migration.sql` includes data backfills. `20261004120000_staff_roles/migration.sql` uses partial unique indexes for active appointments/permissions; preserve these SQL-only invariants as well as the Prisma schema.
- Not every historical migration is purely additive: `20261003120000_room_cup_repeat_per_window/migration.sql` drops a unique index and replaces it with a window-oriented index. Review semantic changes, not merely whether rows are deleted.
- Deployment conventions are mixed: `docs/delivery-2026-09-26.md` documents `prisma migrate deploy`; `ops/deploy-2026-10-14.sh` takes a PostgreSQL dump and applies a migration directly through `psql -1` after a schema check. Before future deployment, reconcile actual schema and `_prisma_migrations` history; do not assume files prove what production applied.
- For this spec, add new timestamped SQL migrations with matching `schema.prisma` changes, nullable/defaulted additions and explicit backfills. Preserve historical gift/CP/agency/inventory rows. Check conflicts before adding uniqueness; remove the invite pair-wide uniqueness only through a reviewed migration. Rehearse on a restored backup. No migration was created or executed in this audit.

### 51. Atomic, idempotent cross-system operations
- Current state: `backend/src/gifts/giftService.ts::sendGiftAtomic` uses Serializable transactions, guarded balance decrement and retry; gift row, lucky settlement, agency commission accrual and sender XP occur inside that transaction. `CpValueEvent` prevents duplicate value entries. However, `backend/src/services/cp.service.ts::sendCpGiftToPartner` commits the gift before `recordCpGiftValue`; `acceptCpRequest` separately claims the invitation, commits the gift, creates/updates the pair and finalizes state. `backend/src/gifts/controller.ts::sendBatch` loops separate gift transactions. Notifications and room-cup evaluation are post-commit best-effort. Store buy/send and room background rental have the limitations identified above. VIP reward grants also use separate writes. Room/seat state is process-local, while financial truth is PostgreSQL.
- Gap: Server-side implementation is substantial, but end-to-end atomicity and recoverable delivery are incomplete. A crash can leave a paid CP gift without CP progression or an invitation stuck accepting; partial batches and missing post-commit rewards/notifications are possible. Request-response idempotency does not guarantee every dependent system processes the committed operation once.
- Plan: Refactor existing services to accept a shared Prisma transaction context: one business commit should include debit/credit, canonical gift/order record, CP changes, required XP/agency/inventory/ID changes, mandatory audit and durable result identity. Reuse the current services rather than duplicating their calculations. Add a small transactional outbox for socket/notification/reward work that must survive process failure, with consumer dedupe keyed by transaction/event and replayable delivery. Keep media failures outside monetary rollback; socket reconnects resync authoritative state. Integrate new rocket/PK contributions and reward claims through those same operation identities. Consolidate entitlement checks, room/seat target validation and all financial permission paths before enabling new features.
- Risk/notes: Cross-system money/progression correctness is the main release risk. Reconcile historical stuck/partial records with an audited, dry-run-first process; do not rerun charges or rewrite historical ledgers blindly. Test race conditions and crash recovery against PostgreSQL, then validate room/audio continuity on devices. A reliable outbox provides eventual delivery; it does not make socket reception itself an atomic database operation.
- Size: L.
